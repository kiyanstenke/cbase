The editor's traps (canvas window under zoom, orientation only through a controller of its own, world origin, SwiftUI gestures
in the scroll view) are explained in the comments of `WorkflowCanvasEditor.swift` and `WorkflowSurface.swift`.
Counterpart on the web: `web/src/components/workflow/`.

Not here: the workflow models (`WorkflowGraph`, `WorkflowNode`, `WorkflowDetail`, `WorkflowRunSettings`, `DynWorkflowSummary`/`DynWorkflowEntry` — `Models/WorkflowModels.swift`);
the RUN of a dynamic workflow in the chat (marks, approval card, progress tree — `Chat/`, section "Dynamic workflows" there);
the progress strip in the chat (`ChatWorkflowStrip` — `Chat/ChatStrips.swift`; workflows are started with `/workflow:<short name>` in the slash picker, `Chat/SlashPicker.swift`).

**The most common questions:**
- Where is an edge drawn? → tapping a dock sets `linkFrom` (`WorkflowCanvasEditor.swift`, `onPort`), the tap on the target's card half completes it via `connect(from:to:branch:fromSide:toSide:)` — the gesture chooses input and output, not the calculation.
- Why is the drawing surface UIKit and no `Canvas`? → header comment of `WorkflowSurface.swift`: a SwiftUI `Canvas` draws only a wrongly computed section under the zoom transform; `CAShapeLayer` edges and a tiled dot grid stay sharp.
- Why does a step show no round cap? → it lies on no cycle: `cycleNodes` (`WorkflowCanvasEditor.swift`, from `WorkflowGeometry.cycleEdges`) decides, `capPlaceholder(_:)` next to it labels the stepper at value 0 with the EFFECTIVE value ("5 · Default" / "20 · from Review") — calculated in `WorkflowRules.capEffective` with an own value of 0 (cycle group in BFS order, on a tie the first source like `governing[0]`; guard `web/test/cap-binding.test.mjs`). The slash picker in the command field uses the SAME functions as the composer (`slashWord(in:)`, `slashSorted` — free functions in `Chat/ChatViewModel+Slash.swift`, no copy), fetches the skills on opening via `effective-skills` and knows NO client commands of the chat. Measured in `CbaseMobileUITests/Tests/CodingUITests.swift` (`testWorkflowNodeSheetShowsCapOnlyInCycleAndSlashPickerKnowsSkills`, on the fixture workflow "Review-Schleife").
- Why does the "Step" menu show an image instead of the `WorkflowBadge`? → a SwiftUI `Menu` hands its buttons to UIKit as a UIMenu, and a menu item there carries only text and image, no view — `WorkflowBadgeImages` (`WorkflowCanvasEditor.swift`, behind `WorkflowBadge`) therefore renders the badge once per type and color scheme with `ImageRenderer` into a 22-pt `UIImage` and keeps it; `.renderingMode(.original)` on the `Image` is mandatory, otherwise the menu tints it as a template. The text stays the item's accessible name. The same badge (22 pt) sits in the header of the step sheet.
- Where is the orientation enforced, where is saving done? → `WorkflowCanvasEditor.swift:WorkflowOrientation.landscapeForce` decides, `WorkflowEditorController.supportedInterfaceOrientations` enforces it (`requestGeometryUpdate` would only be a request); saving is `save(active:)`, `PUT {base}/{id}` with name, description, graph, `lock`, run settings and when arming `active`.
