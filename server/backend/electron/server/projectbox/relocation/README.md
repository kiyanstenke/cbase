# `projectbox/relocation/` — relocating a project into its project container

**What is here:** the internal path that brings a project from the user container (B) into its project container, checks
strictly and only then removes what it moved. No UI and no switch: a relocation begins by hand through the routes below.

| File | What | Guard |
|---|---|---|
| `plan.js` | Step 1, PURE: `planRelocation(data, { under, realPath, exists })` over what the collection gathered (inspect JSON of all containers of B, images, volumes, networks, `docker diff`, Compose texts, worktrees, MCP servers, `readEnvFiles`, services, start scripts, ~/.local, texts, other projects; the shape is in the file header). No docker, no store, no writing; it only reads `realpath`. `ENTRIES` is the ONE table "entry → hold \| hint"; what a copy cannot carry is only named. `RATES` are the assumptions of the downtime estimate; the start order comes from `../restore.js:startStages`. One-off containers (`compose run`, `oneoff=True`) STAY in B: no service, start order, image or volume of theirs is in the plan, only the hint `once-container`; a running one, or one on a volume that moves, holds. Containers of cbase (project container, helper, probe) never count: recognised by EXACTLY the keys of `../own-labels.js` set ON the container (one inherited from the image does not count); if such a container mounts a volume of the plan or has its `working_dir` in the project folder, `container-excluded` holds. The write layer (`docker diff`) holds only when it carries data: not under `DIFF_TRANSIENT`, not a mount target of the container, not what a runtime regenerates (`DIFF_GENERATED`). Processes of B in the project folder hold (`process-in-project`); one in a terminal the lock ends is a hint; a MISSING `processes` field is `data-missing`. `portsInCommand` is the rule of `./port-command.js` and counts only the REGISTERED port; `service-port-collision` holds only for a duplicate the port dismantling CREATES. `worktreePartitioning`/`toMovingWorktrees` compute the worktrees of step 13 ONCE (for `collect.js` too). `applyReceipts` lifts a write-layer hold only for a receipt with the name, count and checksum from the plan. | `server/backend/test/relocation-plan.test.js`, `relocation-plan-procedure.test.js` (real collection + real plan + real procedure against the fake docker) |

Renames and parent folders only inside the area (`renameInArea`, `createFolderInArea`); `runtimeSources` is the ONE list of its sources. **The manifest program** is NOT here: `server/backend/cbase-manifest` (python3), in the backend image under
`/usr/local/bin/cbase-manifest` — that folder is mounted read-only into every project container (`../creation.js`, rule
`system-bin`), so the same program measures in B, in the helper and in the project container. It never prints content:
files, symlink targets and xattr values only as sha256.

**Why manifests instead of size and count?** Size and count are falsely red for a correct copy (directory sizes) and falsely
green for most deliberate faults — among them one flipped character in a Postgres table that Postgres itself does not
notice. The source is measured after stopping (step 4), the target before the start (step 14); a manifest without its
closing line is invalid, not shorter.

**Three typical questions:**

- *Why does a relocation not begin, or why does a container not move along?* The answer of `POST …/relocation` carries
  `code` and `holdReasons` or `open` (`procedure.js:startRelocation`, preconditions). A hold reason: `holdReasons[].kind` →
  `plan.js:ENTRIES[kind]`, every kind has a sentence. A missing container: `plan.js:planRelocation`, section "Who moves
  along" — after realpath its `working_dir` is not UNDER the project folder (with the separator), or it has no Compose label
  (`without-label`), or it carries a cbase key ON the container (`../own-labels.js`; if it hangs on the project,
  `container-excluded` holds). When `process-in-project` holds, the entry names pid, program and start time — a process in
  B working in the project that the relocation does not end itself (`./processes.js`): a dev server from a workspace
  terminal or VS Code, a service started by the agent, a service whose run lost its pid.
- *What happened after an error or restart in the middle of a relocation?* `GET …/relocation` (`relocationStatus`: step,
  direction, end, error, report, duration per step), plus `<data>/relocations/<projectId>/<time>/log.log`. Before the
  turnaround (`start`) the procedure takes the return path (`rw-*`, the `…Back` data steps of `data.js`); a journal without a
  living procedure is decided in the restart grace (`procedure.js:relocationRestartGraceSeam`, registered in `server.js`).
  After the turnaround only forward; if something fails there, the journal stays open and the row `ready` with the reason —
  the next start finishes it, or `POST …/relocation/resume`. The reason of a return path is in `report.returnPath.reason`
  and in the column `error`, every part that did not come back in `report.returnPath.error`; a row in `hold-return-path`
  or `hold-resume` names its way out.
- *Where is an env value stored?* Nowhere except in the backup (0600) in the relocation location, which is never mounted:
  `../env-key.js` hands out only keys and classification, the journal accepts only names (`store/project-relocations.js`
  throws otherwise), and a Compose error arrives blacked out (`procedure.js:composeIn`).

**What is NOT here:** the docker calls (`../docker.js`), the creation (`../creation.js`, `../instance.js`), the paths of the
runtime folder (`runs/runtime-location.js`), the shared leaves `../env-key.js` and `../compose-config.js` (stack copies use
them too).
