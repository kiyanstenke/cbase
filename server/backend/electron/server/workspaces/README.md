# `workspaces/` — workspaces

**What lives here:** `git-auth.js` — managed paths in container operation (`managedPathsOn`, `managedWsRoot`, `managedPath` with `slugify`: workspaces and projects are created by NAME only, the server assigns the folder) and git access (`writeGitAskpass` writes the askpass script at start, `wsForPath` finds the workspace for a path, `gitAuthCtx` returns host + access for network operations, `gitErrPayload` flags auth errors for the access modal), plus `purgeProjectDir` (deleting for good, only in the container and only under `$HOME`).

**Routes (`routes.js`):** `ROUTES` (`server.js`) lists `workspaceListRoutes` (`GET|POST /api/workspaces`) and the **owner `workspaceRoutes`** of the family `/api/workspaces/:wid(/sub)`: preamble (regex, `store.getWorkspace`, 404), then `fctx = { ...ctx, wid, sub, ws }` through the table of sub-slices in order — `coreWorkspaceRoutes` (base GET/PATCH/DELETE, `/overview`), `toolchain/routes.js:toolchainWorkspaceRoutes`, `toolchain/skill-routes.js:skillHistoryWorkspaceRoutes`, `workflows/routes.js:workflowWorkspaceRoutes`, `channels/routes.js:channelWorkspaceRoutes`, `dynworkflows/routes.js:dynWorkflowWorkspaceRoutes`, `outerloop/routes.js:outerLoopWorkspaceRoutes`, `scheduled/routes.js:scheduledWorkspaceRoutes`, `instructions-routes.js:instructionsWorkspaceRoutes`, `tailWorkspaceRoutes` (`/agents[/…]`, `/file-search` (with the limit of the file routes, `code-route.js:fileLimit`: in a converted project the name search follows no link; if the limit throws, 409), `/settings-json`, `/setup-mcp`, `/projects`, `/context` (an unclear dump lands in the workspace dumpster), `/context/ingest` (a Coding chat with its job, `../projects/coding-jobs.js`), `/context-categories`, `/browser/ensure` — and as the LAST branch `devtools/code-route.js:codeRoute(ws.path, sub, …)`: `/files`, `/git`, `/ts`, `/terminal`, `/debug/launch`; `true` means answered, otherwise `return NEXT;`). **The naming convention is a contract of the deploy tool:** workspace sub-slices end in `WorkspaceRoutes` — `getRoutes` in `tools/check/lib/asar.mjs` reads `sub === "/…"` routes ONLY from such functions (`tools/check/routes.test.mjs`). A sub-slice with another suffix would be invisible to the operator's status check.

**What does NOT live here:** the git commands themselves (`../git.js`), persistence (`store/workspaces.js`, `getGitCred`), the code/git/file routes of a folder (`devtools/code-route.js`; the project family carries its own copy `devtools/routes.js:codeProjectRoutes`), the toolchain per workspace (`toolchain/`), cleaning up the chats when a workspace is deleted (through the ONE closing path `../chats/erase.js:closeChats([], () => store.deleteWorkspace(wid).chatIds)`; `coreWorkspaceRoutes` itself only handles the `ws:`/`proj:` shells) and the project containers of its projects (`../projectbox/erase.js:deleteProjectbox` BEFORE everything else — 409/500 there means the workspace stays; a failed `stop` restarts those already stopped, a later abort leaves all rows and names the containers already removed; without an instance row no docker call and the same response). `DELETE /api/workspaces/:wid/projects/:pid` (`tailWorkspaceRoutes`, the button of the web UI) does not delete itself either but through `../projectbox/erase.js:projectDelete` — the same path as `DELETE /api/projects/:id` (a project of another workspace does not touch the container). `DELETE` reads the project list FRESH after `deleteProjectbox` and sends what came into being during the docker steps through the same path (its own `hold`, released last in the finally); the creation POST asks the lock itself (`../projectbox/idle.js:workspaceGetsDeleted` ⇒ 409 `WORKSPACE_GETS_DELETED`).

**Terms (→ file):** workspace, managed path, slug → `git-auth.js` · git access, askpass, auth error → `git-auth.js` · deleting a project folder (container) → `git-auth.js` · creating/changing/deleting a workspace, overview, creating projects, context, settings.json → `routes.js` · instructions for agents (sections per workspace/project, scope, takeover) → `instructions-routes.js`, their one-time migration from the profile files → `instructions-migration.js`.

**The three most common questions:**
- Where do `git push`/`pull` get username and token from without them being visible in the process? → `git-auth.js:gitAuthCtx` (askpass script from `writeGitAskpass`, access per workspace and host). For VS Code in a converted project the git helper fetches the same stored access via `POST /api/workspaces/:wid/git-access` (`tailWorkspaceRoutes`, verdict `../projectbox/git-assignment.js:gitAccessResponse`: only with the ops marker, from loopback and with the key from `<data>/git-access.key`).
- Which folder does a new workspace or a new project get in the container? → `git-auth.js:managedPath` (`slug`, `slug-2`, … under `managedWsRoot`).
- Why does the client show an access modal after a git error — or not? → `git-auth.js:gitErrPayload` (`authRequired` only for a recognized auth error, `ssh` separately).

**The workspace of the git access comes from the CALLER:** `git-auth.js:wsForCode(root, workspaceId)`
(with an id exactly that workspace, otherwise via the path); `gitAuthCtx(root, rel, opts, { workspaceId })`. `devtools/code-route.js`
gets `opts.workspaceId` (project level `proj.workspaceId`, workspace level `ws.id`). With nested workspaces `wsForPath` takes
the INNERMOST (longest path), not the first in the list. Guard `server/backend/test/code-scopes.test.js`.

**Outer loop:** `outerLoopWorkspaceRoutes` (`../outerloop/routes.js`) is in the sub-slice table of `workspaceRoutes` BEFORE
`tailWorkspaceRoutes` (`/api/workspaces/:wid/outer-loop…`). `POST /api/workspaces` seeds the summarizer, the agenda keeper and the
timeline agent (`../outerloop/seed.js`; the start catches up on a missing one). `DELETE /api/workspaces/:id` aborts the open
runs of all outer-loop agents of the workspace before the closing path (`../outerloop/abort.js:abortOuterLoop` — deleting
ends them, no 409); `store.deleteWorkspace` takes the rows.

**Project creation:** a project is created only via `POST …/projects` (the button of the UI). The former routes
`GET /api/workspaces/:wid/detect-projects` and `POST /api/workspaces/:wid/projects/import` answer 404 — the import created projects
WITHOUT a container in ops mode. `HEAVY_DIRS` stays (`../files.js`, tree and search). Guards: `tools/check/routes.test.mjs`
(`GONE_SINCE_SPLIT`, `GONE_WITHOUT_GET`), `server/backend/test/tool-list-without-project-create.test.js` (404 on the real server),
`web/test/project-creation-legacy-data.test.mjs` (no client calls them).

**A workspace's time zone (`timeZone.js`):** a leaf (store and `../cron.js`) — `timeZoneDefault(wid)` reads the zone a client chose last (key `timeZone.<wid>`, default UTC, the container runs in UTC), `rememberTimeZone(wid, tz)` sets it only when valid. The writer is creating and changing a scheduled job (`../scheduled/routes.js`), readers are the outer loop (clock times, wall time), `../communication/retrieval.js` and `../channels/delivery.js`. Falls with the workspace (`store/workspaces.js`: every setting ending in `.<wid>`).

**Instructions for agents:** `instructions-routes.js` (`instructionsWorkspaceRoutes`) — `GET|POST /api/workspaces/:wid/instructions`, `PUT|DELETE …/:aid` (with `version`, 409 for a stale state), `PUT …/order`, `PUT …/:aid/takeover` (opt-out of a workspace section per project), `GET …/:aid/history`; every field required (400), cap `INSTRUCTIONS_CAP` (text 20,000, title 80, 30 per level), event `instructions`. From project networks there is no row in the fence table (rejected) — only the human maintains them. Stored in `../store/instructions.js`, computed in `../toolchain/instructions.js`, carried by every main run, subagent and workflow agent of every provider. `instructions-migration.js`: once per store (marker `instructions.profile_migration`) a profile with text and a workspace binding becomes a section "Persona" (scope `main`); called in `server.js` at start. Guards `server/backend/test/instructions.test.js`, `system-prompt-findings.test.js`.
