# `lib/api/` — the web client's API client, in parts

`lib/api.ts` is only the facade (`export * from "./api/<part>.js"`); **importers stay with `@/lib/api`** — no importer in
the repo reaches into a part directly. Each part is a leaf module: it imports NOTHING outside `lib/api/`, so the tests can
compile it without a tsconfig (an `@/` import would not resolve there). Use `import type` for types and value imports
only for functions and constants. `events.ts` imports the type `ChatJob` from `scheduled.ts` only as `import type`.

**Why `.js` in the imports** (`from "./core.js"`, in the facade `./api/core.js`): `web/test/global-events.test.mjs`
compiles `lib/api.ts` with tsc WITHOUT a tsconfig and loads the result as ESM in Node — Node does not search for
extensions, and tsc passes specifiers through unchanged. `moduleResolution: "bundler"` (tsconfig) resolves `.js` to
`.ts`; webpack does so only with `experimental.extensionAlias` in `next.config.ts` (set there). A new part: imports with
`.js`, add an `export *` line to `lib/api.ts`.

Conventions that hold across the parts:

- Every response goes through a `norm*` function with a default per field. A default never claims what the server did
  not say: a missing number is `null`, never 0; an unknown status is `null` or an explicit fallback, never a made-up one.
- Request bodies are typed objects, not conditional spreads, and carry EVERY required key (also as `null`);
  `web/test/seams-fields.test.mjs` reads the fields via the type checker and holds them against the routes.
- Lists that belong to a contract on the server or gateway are mirrored as constants and bound to the types
  (`*_TYPES_BOUND`) and, in a binding test, to the contract.
